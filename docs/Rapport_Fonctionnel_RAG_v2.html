Partie 1

P1Le Pitch

Le problème

Les experts en accessibilité web passent des heures à rédiger les mêmes rapports Word, audit après audit. Les mêmes erreurs reviennent, mais aucun outil ne capitalise cette connaissance. Résultat : travail répétitif, lent, expertise silotée dans des fichiers Word isolés.

1
Extraction automatique

Lit les rapports Word .docx et extrait toutes les erreurs structurées.

2
Capitalisation intelligente

Stocke les erreurs dans une bibliothèque dédupliquée — 1 entrée par erreur unique avec un compteur d'occurrences.

3
Augmentation IA

Assistant IA qui répond aux questions en s'appuyant sur vos audits passés et le RGAA officiel.

💡 En une phraseRGAA Constat Extractor transforme des rapports Word en une base de connaissance intelligente, augmentée par l'IA.

2.2Modules Fonctionnels — Détail Complet

Module 1 — Parseur Word parser.ts

Rôle : Transformer un buffer binaire .docx en tableau ExtractedFinding[].
Pourquoi : Les rapports sont en Word. L'application extrait des données structurées sans intervention humaine.

Flux interne du parseur
flowchart LR A["Buffer .docx"] --> B["mammoth.js"] B --> C["Texte brut"] & D["HTML + liens"] C --> E["parseTextContent()"] D --> F["extractAuditedPages()"] E --> G["ExtractedFinding[]"] F --> H["AuditedPage[]"] G & H --> I["ParseResult"]
1
Double extraction

mammoth lit le .docx deux fois : texte brut (constats) + HTML (liens des pages auditées).

2
Localisation de section

Utilise lastIndexOf() pour trouver la dernière occurrence de "Descriptions des erreurs" — la première est dans le sommaire.

3
Détection critères

Regex /^Critère\s+[\d.]+/i pour identifier chaque critère RGAA.

4
Extraction + séparation

Regex Impact\s*:\s*(Bloquant|Majeur|Mineur) pour les constats. Pattern /[.!?][A-Z]/ sépare le constat de sa solution.

ChampTypeDescription
thematicNumbernumberNuméro de thématique (1–13)
criterionReferencestringRéférence ex: "1.1"
impactBloquant│Majeur│MineurNiveau de criticité
findingstringTexte du constat
solutionstring?Correction suggérée

Module 2 — Dédoublonnage deduplication.ts

Rôle : Générer une empreinte unique (signatureHash) pour chaque constat.
Pourquoi : Sans dédoublonnage, 50 audits avec la même erreur créeraient 50 entrées. On veut 1 entrée avec occurrenceCount = 50.

// Étape 1 — Normalisation sévère
"L'image du Lôgo n'a PAS d'alt !" → "limage du logo na pas dalt"

// Étape 2 — Hash SHA-256
SHA-256("limage du logo na pas dalt" + criterionId) → "a3f8c1d9..."

// Étape 3 — Upsert
hash inconnu → INSERT finding_template (nouveau)
hash connu   → UPDATE occurrenceCount++ (existant)
⚡ ImportantLa signatureHash est la clé de déduplication stockée dans MySQL et aussi l'ID stable dans ChromaDB.

Module 3 — Stockage Hybride storage.ts

Rôle : Abstraire le stockage des fichiers .docx — le reste du code appelle toujours storagePut(), storageGet(), storageDelete() sans savoir où les fichiers vont réellement.

Variable d'envModeComportement
FORGE_API_KEY absentLocalFichiers dans ./uploads/{userId}/
FORGE_API_KEY présentCloud S3Proxy vers AWS S3 via l'API Forge

Module 4 — Cerveau d'Audit RAG server/hub/

💡 VisionLe Cerveau d'Audit est un système multi-RAG orchestré. Plusieurs RAG spécialisés collaborent pour produire des réponses fiables, sourcées et zéro hallucination. Chaque RAG est administrable : ajout, modification, désactivation ou suppression sans toucher au code.

A — Orchestrateur (orchestrator.ts)

Le cerveau du système. Il analyse l'intention de chaque requête, sélectionne les RAG pertinents et choisit la stratégie de collaboration.

Architecture globale — 7 couches du Cerveau d'Audit
flowchart TB E0["🖥️ Interface web · MCP · Screenshot"] E0 --> O["🧠 Orchestrateur — Analyse intention · Sélectionne RAG · Stratégie pipeline"] O --> R1["RAG 1 Rapports d'audit"] O --> R2["RAG 2 RGAA 4.1 officiel"] O --> R3["RAG 3 Remarques / Formules"] O --> RN["RAG N+1 Extensible"] R1 & R2 & R3 & RN --> RH["🔍 Retrieval hybride — Vectoriel · Exact · Re-ranking BM25"] RH --> CG["🛡️ Context Guard — Score confiance · Seuil · Signal si insuffisant"] CG --> LM["⚡ LLM via OpenRouter — Modèle configurable · Citations obligatoires"] LM --> RS["✅ Réponse structurée — Critères · Sources · Score · Mode"]

Trois stratégies d'orchestration selon le type de requête :

StratégieDéclencheurFonctionnement
A — SéquentielleAnalyse code, critère précisRAG 1 propose → RAG 2 valide → RAG 3 enrichit. La plus fiable.
B — ParallèleQuestion libre accessibilitéTous les RAG actifs répondent en simultané → fusion par score.
C — ManuelleMode expert utilisateurL'utilisateur choisit quels RAG interroger (RAG 1 seul, RAG 1+3…).

B — RAG Spécialisés (hub/rags/)

Chaque RAG est un module indépendant avec sa propre collection ChromaDB, son seuil de similarité et son poids dans le scoring.

RAGCollection ChromaDBPrioritéPoidsSeuilRôle
RAG 1 — Rapportsrgaa_findings1ère — source primaire1.4×0.68Constats et solutions issus de vos audits réels. Mine d'information principale.
RAG 2 — RGAA officielrgaa_referential2ème — validation1.6×0.80106 critères indexés avec procédure de test structurée, non-applicabilités et niveau WCAG A/AA.
RAG 3 — Remarquesrgaa_notes3ème — enrichissement1.2×0.65Notes expertes ajoutées manuellement. Règles sur les confusions fréquentes entre critères.
RAG N+1configurableLibreconfigurableconfigurableExtensible sans code : WCAG 2.2, règles client, bibliothèque de composants conformes…
⚡ CritiqueL'indexation ChromaDB est toujours en fire-and-forget (setImmediate). Si ChromaDB est hors ligne, l'import MySQL réussit quand même. Le métier n'est jamais bloqué par l'IA.

C — Procédure de détection du bon critère

⚠️ Zone sensibleUne erreur d'accessibilité peut toucher plusieurs critères simultanément. Le système ne se verrouille jamais sur le premier candidat — il parcourt tous les candidats avant de conclure. C'est la garantie d'une attribution correcte.
Pipeline de détection multi-critères en 6 phases
flowchart TB P0["Phase 0 — Entrée brute Erreur · code · question · screenshot"] --> P1 P1["Phase 1 — Extraction des symptômes Éléments HTML · rôles ARIA · type de contenu"] --> P2 P2["Phase 2 — Mines d'information RAG Rapports + RAG Remarques — patterns réels validés"] --> P3 P3["Phase 3 — Pool de critères candidats Critères probables triés par score composite"] --> P4 P4["Phase 4 — Parcours RGAA exhaustif Méthode de test officielle pour chaque candidat Vérification non-applicabilité en priorité"] --> P5 P5["Phase 5 — Arbitrage 1 critère / multi-critères / hors périmètre"] --> P6 P6["Phase 6 — Réponse finale Critère principal · Secondaires · Score par critère · Preuve · Sources"]

L'ordre des phases est fondamental : on consulte d'abord le RAG Rapports et le RAG Remarques (mines d'expérience réelle), puis le RAG RGAA vient valider et éliminer les candidats via ses procédures de test officielles — jamais l'inverse.

D — Indexation enrichie du RAG RGAA

Chaque critère RGAA est indexé avec trois dimensions supplémentaires par rapport à un simple texte vectorisé :

DimensionContenuUtilité
Procédure de test structuréeArbre conditionnel JSON (elements_cibles, step_1…N, pass_if, fail_if)Permet d'exécuter les tests pas à pas, pas seulement de les lire
Conditions de non-applicabilitéListe JSON des exclusions (ex : image décorative, role=presentation)Vérifiées EN PRIORITÉ avant le scoring → évite les faux positifs
Niveau WCAG A/AAwcag_level, wcag_ref, scoring_boost (×1.3 si niveau A)Les non-conformités légalement prioritaires remontent toujours en tête

E — Formule de scoring enrichie

score = similarité_cosine × poids_collection
      + boost_wcag_A (×1.3 si level = A)      ← priorité légale
      + log(occurrenceCount) / 5               ← expérience réelle
      + (confidenceLevel / 100) × 0.2          ← confiance expert
      − pénalité si non-applicabilité détectée ← anti faux-positif

F — Embeddings (embeddings.ts)

Convertit du texte en vecteur (~1500 nombres). Deux textes sémantiquement proches ont des vecteurs proches → ChromaDB les trouve par similarité cosine.

"L'image n'a pas d'alt"     → [0.12, -0.87, 0.43, ...]
"Texte alternatif manquant" → [0.11, -0.85, 0.41, ...]  ← proches !

G — Context Guard — Anti-hallucination (hub/contextGuard.ts)

Avant d'envoyer un contexte au LLM, le Guard vérifie trois conditions. Si le seuil n'est pas atteint, la réponse est transparente sur ses limites — le LLM n'invente jamais.

VérificationConditionComportement si échoue
Score minimumMeilleur score ≥ 0.72 (similarité cosine)Mode insufficient — réponse honnête sur le manque de données
Couverture multi-sources≥ 2 sources indépendantes concordantesMode insufficient — une seule source n'est pas suffisante
Non-applicabilitéAucune condition d'exclusion active dans le contexteCritère écarté + message explicatif affiché
Mode réponseConditionCe que voit l'utilisateur
ragContexte suffisant, score ≥ seuilRéponse complète avec critères, sources et score de confiance
rag-cold-startChromaDB vide ou RAG non encore indexéRéponse LLM seule, signalée clairement comme non sourcée
degradedChromaDB hors ligneRéponse LLM seule avec avertissement
insufficientScore trop faible ou sources contradictoiresMessage transparent : "données insuffisantes" + ce que le RGAA dit

H — LLM via OpenRouter (hub/llmAdapter.ts)

Le modèle IA est configurable sans redéploiement depuis l'interface d'administration. OpenRouter donne accès à tous les grands modèles via une seule API.

ParamètreValeur par défautDescription
modelgpt-4oModèle principal — modifiable sans code
fallback_modelclaude-sonnetActivé si le modèle principal est indisponible
temperature0.1Très basse : réponses précises et reproductibles
citations_requiredtrueLe LLM doit citer ses sources — instruction prompt système

I — Administration des RAG (hub/ragAdmin.ts)

Les RAG sont gérés via un registre rag_sources en base. L'interface d'administration expose les quatre opérations :

ActionEffetsDonnées préservéesRègle de garde
CréerFormulaire → provisioning ChromaDB → indexation → activation—Slug unique requis
ModifierConfig légère (poids, seuil, topK) sans réindexation. Config lourde (embedding) → réindexation forcéeToutesVersioning automatique
DésactiverRetiré du pipeline immédiatement. Réactivation en 1 clic.ChromaDB + MySQL intacts1 RAG actif minimum requis

Chaque RAG est monitoré en continu : nombre de requêtes, score de confiance moyen, pourcentage de mode insufficient, latence. Les requêtes échouées alimentent la base d'amélioration continue du RAG 3 (Remarques).
